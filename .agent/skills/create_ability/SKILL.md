# 기능: 어빌리티 생성 (`create_ability`)

이 스킬은 보편 어빌리티 문법 v2를 기준으로, 캐릭터나 몬스터를 위한 어빌리티를 생성하고 검증하는 도구입니다.

핵심 역할은 세 가지입니다.

1. 구조적으로 일관된 어빌리티를 제안한다.
2. 리포트를 먼저 작성하여 검토 가능 상태로 만든다.
3. 승인 후에만 실제 데이터에 반영한다.

---

## 1. 참조 기준

반드시 아래 문서를 함께 참조한다.

1. `manuals/99-1_ability_syntax.md`
2. `manuals/99-2_ability_tags.md`
3. `manuals/97_trait_and_naming_rules.md`

---

## 2. 핵심 규칙

### 2-1. 보편 문법 준수

모든 어빌리티는 아래 내부 정규 문법을 따른다.

`[층위/표현권역:세부원천] - [계통] - [형태] -> [효과]`

표시용 축약 문법은 필요 시 아래를 사용한다.

`[표현권역:원천] - [계통] - [형태]`

### 2-2. 구조 필드 우선

어빌리티를 만들 때는 먼저 아래 구조 필드를 결정한다.

1. 층위
2. 표현 권역
3. 원천
4. 계통
5. 형태
6. 효과

그 다음에야 발동 방식, 비용, 리스크, 태그를 붙인다.

### 2-3. 태그는 보조 계층

태그는 구조를 대신 설명하면 안 된다.

비권장:

- `#방출`
- `#투사체`
- `#피해`

권장:

- `#화염`
- `#폭발`
- `#광역`
- `#고위험`

### 2-4. 선-리포트 후-저장

생성 결과를 즉시 `data/`에 저장하지 않는다.

반드시 다음 순서를 따른다.

1. 제안 생성
2. 검증
3. 리포트 작성
4. 사용자 승인
5. 데이터 반영

---

## 3. 생성 프로세스

### 단계 1. 요청 해석

사용자의 요청에서 다음을 추출한다.

1. 능력의 컨셉
2. 장르적 표현 방식
3. 사용 주체
4. 기대 효과
5. 제약 또는 대가

### 단계 2. 구조 설계

각 제안은 아래 순서로 설계한다.

1. **층위**: 무엇을 건드리는가
2. **표현 권역**: 작품 안에서 어떻게 보이는가
3. **원천**: 어떤 재료/근원으로 작동하는가
4. **계통**: 어떤 방식으로 작동하는가
5. **형태**: 어떤 발현 모양 또는 매체로 나타나는가
6. **효과**: 결과적으로 무엇이 바뀌는가

### 단계 3. 운용 메타 부여

각 어빌리티에 아래를 붙인다.

1. 발동 방식
2. 지속 방식
3. 비용
4. 리스크
5. 태그

### 단계 4. 브레인스토밍 확장

기본 제안을 만든 뒤, 아래 방향으로 변주를 확장할 수 있다.

1. 상위 출력형
2. 저비용 실전형
3. 고위험 필살기형
4. 방어/보조 전환형
5. 약화/교란 전환형
6. 집단전 특화형
7. 패시브화 변주
8. 조건반응형 변주

---

## 4. 검증 규칙

### 4-1. 구조 검증

아래를 확인한다.

1. 층위와 표현 권역이 서로 모순되지 않는가
2. 원천이 허용된 원천 대분류 안에 드는가
3. 계통이 작동 방식으로 읽히는가
4. 형태가 발현 모양 또는 매체로 읽히는가
5. 효과가 결과 상태로 읽히는가

### 4-2. 축 충돌 검증

같은 개념이 여러 축에 중복 배치되면 안 된다.

예:

- `반사`를 계통으로 썼다면 효과에는 `되튕김`처럼 결과를 써야 한다.
- `낙인`을 형태로 썼다면 효과에는 `추적`, `약화`, `봉인` 등을 쓴다.

### 4-3. 태그 검증

태그는 아래 기준으로 검증한다.

1. 구조 필드 중복 여부
2. 표준 태그로 치환 가능 여부
3. 태그 수 적정성
4. 새 태그의 필요성

---

## 5. 리포트 작성 규칙

리포트는 `report/ability/`에 작성한다.

파일명 예시:

`report/ability/[YYYYMMDD]_[주제]_생성리포트.md`

리포트에는 최소한 아래가 포함되어야 한다.

1. 제안된 어빌리티 목록
2. 각 어빌리티의 구조
3. 발동 방식 / 비용 / 리스크
4. 태그
5. 새로 제안된 태그나 원천
6. 적용 예정 경로
7. 검토 요청 메모

---

## 6. 리포트용 출력 스키마

```markdown
| 이름 | 구조 | 발동 방식 | 비용 | 리스크 | 태그 | 설명 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 화염구 | [물질/마도:화염] - [방출] - [투사체] -> [피해/폭발/화상] | 즉발 | 마력 | 반동 | #화염 #폭발 #광역 | 응축한 화염을 투사체로 발사해 폭발시킨다. |
```

---

## 7. 데이터 반영 원칙

승인 후 실제 데이터 반영 시에는 현재 저장 구조를 따른다.

- 경로: `data/ability/detailed_lists/[권역]권역/[권역]_[계통]계_[형태].md`

단, v2 문법의 전체 구조를 잃지 않도록 리포트에는 반드시 전체 구조를 남긴다.

즉:

1. **리포트에는 전체 구조를 기록**
2. **데이터 파일에는 기존 저장 규칙에 맞게 필요한 항목만 반영**

---

## 8. 작성 지침

1. 모호한 멋있는 이름보다 구조적으로 분해 가능한 능력을 우선한다.
2. 계통, 형태, 효과가 겹치면 먼저 축 충돌을 해소한다.
3. 패시브는 별도 종으로 보지 않고 `발동 방식 = 상시`로 처리한다.
4. 특정 세계관 용어가 필요하더라도 먼저 보편 문법으로 환원한 뒤 다시 이름을 입힌다.
